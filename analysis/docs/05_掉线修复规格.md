# 周期性掉线（Kick）根因与修复规格

**背景**：注入模块后，QQ 每隔一段时间被强制下线。
**结论**：这是**定时体检**（1800 秒周期），并非实时检测。QQ 周期扫描进程内的模块痕迹，上报服务端后触发踢线。

---

## 一、根因证据

### 1.1 时间常量（静态确认）

| 库 | 常量 | 含义 | 出现次数 |
|---|---|---|---|
| `libfekit.so` | `1800` | 30 分钟（秒） | **×4** |
| `libfekit.so` | `5400` | 90 分钟（秒） | ×1 |
| `libbasic_share.so` | `1800` | 30 分钟 | **×7** |
| `libbasic_share.so` | `5400` | 90 分钟 | ×1 |
| `libbasic_share.so` | `60000` | 1 分钟（毫秒） | ×4 |
| `libMSFKernel.so` | `1800` | 30 分钟 | ×3 |
| `libMSFKernel.so` | `300000` | 5 分钟（毫秒） | ×1 |

三个独立库都出现 `1800`，单位统一是**秒**。不是巧合。

### 1.2 触发链（结合已有分析）

```
[1800s 定时器到期]
   ↓
RuntimeEnvCensorTask / DlVmTask   （libfekit 内的任务名）
   ↓
dl_iterate_phdr()        ← 7 个库全部导入
   ↓
  回调拿到每个已加载 ELF 的完整路径：
  /data/app/~~xxx==/com.xxx.module-yyy==/lib/arm64/libzzz.so
  ↑ 路径里直接包含模块包名
   ↓
fopen("/proc/self/maps")  ← 二次确认
   ↓
trpc.o3.report.Report.SsoReport   （上报通道）
   ↓
服务端判定 → StatSvc.ReqMSFOffline (2012) → 客户端踢线
```

### 1.3 为什么改 so 名字没用

`dl_iterate_phdr` 返回的是**加载路径**，格式固定：

```
/data/app/~~<hash>==/<包名>-<hash>==/lib/arm64/<文件名>.so
```

包名是 Android 安装时写死的，**改名、混淆、去字符串都改不掉路径**。

## 二、修复规格：三个必须 hook 的点

### 2.1 `dl_iterate_phdr` —— 第一优先级

**位置**：`libdl.so` / `libc.so`（Android 7+ 在 libc）

**原型**：

```c
int dl_iterate_phdr(
    int (*callback)(struct dl_phdr_info *info, size_t size, void *data),
    void *data
);
```

**结构体**（AArch64）：

```c
struct dl_phdr_info {
    ElfW(Addr)        dlpi_addr;
    const char       *dlpi_name;        // ← 关键：完整路径
    const ElfW(Phdr) *dlpi_phdr;
    ElfW(Half)        dlpi_phnum;
    /* 以下仅 Android 6+ 且 size 足够时有效 */
    uint64_t          dlpi_adds;
    uint64_t          dlpi_subs;
    size_t            dlpi_tls_modid;
    void             *dlpi_tls_data;
};
```

**过滤逻辑**：

```c
static int fake_dl_iterate_phdr(
        int (*cb)(struct dl_phdr_info*, size_t, void*), void *data) {

    int (*orig)(int (*)(struct dl_phdr_info*, size_t, void*), void*)
        = real_dl_iterate_phdr;

    // 用一个中间回调包一层
    struct ctx { int (*user_cb)(struct dl_phdr_info*, size_t, void*);
                 void *user_data; } c = { cb, data };

    return orig(my_callback, &c);
}

static int my_callback(struct dl_phdr_info *info, size_t size, void *p) {
    struct ctx *c = (struct ctx *)p;

    const char *name = info->dlpi_name;
    if (name && name[0] && is_module_path(name)) {
        // 直接把名字清空 —— 主程序本身的 dlpi_name 就是空串，
        // 这样伪装成"主程序镜像"，最自然
        struct dl_phdr_info copy = *info;
        copy.dlpi_name = "";
        return c->user_cb(&copy, size, c->user_data);
    }
    return c->user_cb(info, size, c->user_data);
}
```

**判定 `is_module_path`**（按危险度排序）：

```c
static bool is_module_path(const char *p) {
    // 1. 模块的 so 路径都带包名
    static const char *kws[] = {
        "lsposed", "lspd", "xposed", "edxposed", "riru", "zygisk",
        "magisk", "kernelsu", "apatch", "shamiko",
        "qauxv", "qnotified", "qqbypass", "dexkit", "lspatch",
        "libriru", "liblspd", "libbytehook", "libshadowhook",
        "libdexkit", "libnative-bypass",
        nullptr
    };
    for (int i = 0; kws[i]; i++)
        if (strcasestr(p, kws[i])) return true;

    // 2. 非 /system、/vendor、/apex、/data/app/com.tencent 之外的第三方路径
    if (strstr(p, "/data/app/") || strstr(p, "/data/data/")) {
        if (!strstr(p, "com.tencent.mobileqq")) return true;
    }
    return false;
}
```

> **为什么清空而不是改名**：`dlpi_name` 为空是**主程序镜像**的正常形态（`dl_iterate_phdr` 遍历到的第一个就是主程序，其 `dlpi_name` 是 `""`）。改成伪造名字反而引入新特征。

### 2.2 `/proc/self/maps` —— 第二优先级

**位置**：`libc.so` 的 `fopen` / `open` / `openat` / `fgets` / `fread`

**难点**：`fopen` 返回 `FILE*`，不能简单返回假数据。必须构造一个**内容过滤过的虚拟文件**。

**方案 A（推荐）：构造过滤后的临时文件**

```c
static FILE* fake_fopen(const char *path, const char *mode) {
    if (path && (strcmp(path, "/proc/self/maps") == 0 ||
                 strcmp(path, "/proc/self/smaps") == 0)) {
        return build_filtered_proc(path);
    }
    return BYTEHOOK_CALL_PREV(fake_fopen, path, mode);
}

static FILE* build_filtered_proc(const char *path) {
    // 1. 真实读取
    FILE *f = BYTEHOOK_CALL_PREV(fake_fopen, path, "r");
    if (!f) return NULL;

    // 2. 逐行过滤
    char line[4096];
    char *buf = NULL;
    size_t cap = 0, len = 0;
    FILE *mem = open_memstream(&buf, &len);
    while (fgets(line, sizeof(line), f)) {
        if (is_module_line(line)) continue;   // 丢弃含模块的行
        fputs(line, mem);
    }
    fclose(f);
    fclose(mem);

    // 3. 用 fmemopen 返回（需要 fd，改用 memfd 更稳）
    FILE *out = fmemopen(buf, len, "r");
    /* 注意：fmemopen 的 FILE* 没有真实 fd，
       调用 fileno() 的代码会失败 —— 见方案 B */
    return out;
}
```

**方案 B（更彻底）：`open` 返回 memfd**

```c
static int fake_open(const char *path, int flags, ...) {
    if (is_proc_maps(path)) {
        int fd = syscall(SYS_memfd_create, "maps", 0);
        write(fd, filtered_content, filtered_len);
        lseek(fd, 0, SEEK_SET);
        return fd;
    }
    return BYTEHOOK_CALL_PREV(fake_open, path, flags);
}
```

`memfd_create` 创建的内存文件是**真实 fd**，`fileno()` / `fstat()` / `mmap()` 全部正常工作。这是 QB 项目"虚拟文件描述符"做法的原理。

**需要过滤的行特征**：

```
包含以下任意一项就丢弃：
  lsposed / lspd / xposed / edxposed / riru / zygisk
  magisk / kernelsu / apatch / shamiko
  qauxv / qnotified / lspatch / dexkit
  bytehook / shadowhook
  /data/app/~~*/<非com.tencent.mobileqq包名>*/
  匿名可执行段（rwxp / r-xp 且 inode=0 且 pathname 为空且大小异常）
```

### 2.3 `bytehook_get_records` / `bytehook_dump_records` —— 第三优先级

**背景**：`librmonitor_base.so` 内嵌 bytehook 1.0.10，导出 20 个 API：

```
bytehook_init             bytehook_get_records
bytehook_add_ignore       bytehook_dump_records
bytehook_hook_single      bytehook_get_prev_func
bytehook_hook_all         bytehook_unhook
bytehook_hook_partial
bytehook_add_dlopen_callback
...
```

**问题**：如果模块也链接 `libbytehook.so`，Android linker 按 soname 去重，**双方共享同一个实例和同一张 records 表**。QQ 调 `bytehook_get_records()` 就能列出你装的所有 hook。

**两个解法**：

**解法 1：hook 掉查询接口**

```c
typedef struct {
    struct { void *data; size_t len; } records;   // 实际结构见 bytehook.h
    size_t len;
} bh_records_t;

static int fake_bytehook_get_records(bytehook_stub_t stub,
                                     void **records, size_t *len) {
    // 只返回 QQ 自己的 hook，过滤掉模块的
    // 简单做法：直接返回 0 条
    if (len) *len = 0;
    if (records) *records = NULL;
    return 0;
}
```

**解法 2：不共用实例（更彻底）**

给模块的 bytehook **改 soname**：

```cmake
# 模块的 CMakeLists.txt
set_target_properties(bytehook PROPERTIES OUTPUT_NAME "bh_mod_private")
```

这样加载时 soname 变成 `libbh_mod_private.so`，与 QQ 的 `libbytehook.so` 是**两个独立实例**，records 表不互通。

> **注意**：解法 2 有个副作用 —— 两个 bytehook 实例可能互相 hook 对方的 PLT，造成冲突。QB 项目的 `QAuxvCompatHook.java` 就是处理这类问题的。

## 三、必须同时满足的前置条件

### 3.1 hook 必须在 `Application.attach` 之前完成

定时器的起点是 **QQ 进程启动**，不是模块加载。如果 hook 装晚了，第一次体检（1800 秒后）可能已经跑过。

**正确时机**：

```java
// LSPosed 的 IXposedHookLoadPackage
public void handleLoadPackage(LoadPackageParam lpparam) {
    // 这个回调在 Application 构造之前
    // 此时立刻装 native hook
    NativeBypass.install();
}
```

**错误时机**：

```java
// 等 QQ 初始化完再装，已经晚了
XposedHelpers.findAndHookMethod(Application.class, "onCreate", ...);
```

### 3.2 `dl_iterate_phdr` 是"7/7 全覆盖"的函数

静态分析确认：**7 个高检测强度库全部导入 `dl_iterate_phdr`**。

| 库 | dl_iterate_phdr |
|---|---|
| libfekit | ✓ |
| libMSFKernel | ✓ |
| librmonitor_base | ✓ |
| libbasic_share | ✓ |
| libBugly_Native | ✓ |
| librmonitor_memory | ✓ |
| libbugly_dumper | ✓ |

**守住这一个函数，等于一次覆盖全部 7 个库的枚举路径。** 这是投入产出比最高的一点。

### 3.3 别忘了 `svc #0`

静态扫描发现 **116 处直接系统调用**：

| 库 | svc #0 数量 |
|---|---|
| libMSFKernel | 66 |
| libfekit | 58 |
| libQSec | 7 |
| librmonitor_base | 5 |
| librmonitor_memory | 5 |
| libbasic_share | 5 |
| libBugly_Native | 2 |
| libturingxq | 1 |
| libturingmfa | 1 |

**如果这些库在某些路径上改用 `svc #0` 直接读 maps，libc hook 会失效。**

需要额外 hook `syscall()` 函数本身，或者在 `svc` 指令处下 inline hook（ByteHook 支持）。

优先处理 `libQSec.so` —— 28 KB，7 处 svc 集中在 `0x1da8-0x1e10` 一个函数里，容易定位。

## 四、验证方法

### 4.1 打时间戳定位周期

在 `KickDiag` 里加启动时间记录：

```java
private static final long START = SystemClock.elapsedRealtime();

// 踢线回调里
log("[KICK] 距启动 " + (SystemClock.elapsedRealtime() - START) / 1000 + " 秒");
```

**判读**：

| 距启动时间 | 结论 |
|---|---|
| ≈ 1800s（±30s） | ✅ 定时体检，按本文档三条修复 |
| ≈ 1800s 的整数倍 | ✅ 同上，可能是多次累计 |
| 不固定（几分钟到几小时） | ❌ 不是定时器，是触发式（某次请求带回风控标记） |
| 立即（<60s） | ❌ 启动时就被检测到，hook 装晚了 |

### 4.2 验证 `dl_iterate_phdr` 是否被调用

在 fake 版本里计数：

```c
static int my_callback(struct dl_phdr_info *info, size_t size, void *p) {
    g_dl_iter_calls++;
    if (is_module_path(info->dlpi_name)) {
        g_module_hits++;
        LOGI("dl_iterate_phdr 命中模块: %s", info->dlpi_name);
    }
    ...
}
```

**如果 `g_module_hits` 有增长 → 模块确实被枚举到了，修复有效。**

### 4.3 对照实验

| 组 | 配置 | 预期 |
|---|---|---|
| A | 只装模块，不做任何 hook | 1800s 后被踢 |
| B | 只 hook `dl_iterate_phdr` | 可能仍被踢（maps 那路没堵） |
| C | hook `dl_iterate_phdr` + `maps` | 应能超过 1800s |
| D | C + `bytehook_get_records` | 稳态 |

**做 B 组是关键** —— 它能证明 `dl_iterate_phdr` 是不是主路径。

## 五、如果三条都做了还被踢

说明检测不在客户端，而在**服务端侧的历史画像**。

可能原因：

1. **账号/设备已被标记** —— 服务端有持久记录，客户端再干净也没用
2. **报文字段异常** —— 某次请求的签名/设备字段不一致，服务端认为会话可疑
3. **不是环境检测触发** —— 是会话票据（A2/D2/SKey）过期，跟模块无关

**这种情况的正确做法不是继续堵检测，而是换账号/换设备验证假设。**

## 八、优先级总结

| 优先级 | 动作 | 预期收益 |
|---|---|---|
| **P0** | hook `dl_iterate_phdr`，清空模块的 `dlpi_name` | 一次覆盖 7 个库的枚举 |
| **P0** | 模块 bytehook 改 soname，避免共用 records 表 | 断掉 hook 枚举 |
| **P1** | hook `fopen`/`open` on `/proc/self/maps`，返回过滤内容 | 断掉二次确认 |
| **P1** | `KickDiag` 加启动时间戳，确认 1800s 周期 | 验证假设，避免白做 |
| **P2** | hook `bytehook_get_records` 返回空 | 兜底 |
| **P2** | 分析 `libQSec.so` 的 7 个 svc，看是否走内核直读 | 堵最后一条路 |
