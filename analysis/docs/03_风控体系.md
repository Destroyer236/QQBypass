# QQ 9.3.65 风控体系研究报告

- 样本 SHA-256：`F63ECBAC6980D2109A7CEB854DB0324668B1318CF50C884C0E7C35752CFFEF84`
- 方法：纯静态（apktool / baksmali / 自写 DEX 解析器与 ELF 解析器）
- 覆盖范围：`com.tencent.mobileqq.qsec.*`（24 类）、`com.tencent.mobileqq.sign.*`、`com.tencent.mobileqq.fe.*`、`oicq.wlogin_sdk.*` 相关路径、`libQSec.so` / `libfekit.so` / `libmsfbootV2.so`、`txsfcfg.dat` / `qself.dat`

## 1. 一句话结论

QQ 的风控不是单一 SDK，而是一个 **「三条签名链路 + 一条 PB 事件通道 + 一个远端下发的定时任务体系」** 的四层结构。Java 侧只做路由和参数装配，**所有密码学原语都在 native**，且真正执行哪个签名算法由**服务端下发的 `sign_strategy` 字段**决定。

最反直觉的一点：**`QSec.detectMethod`（反射反 Hook 检测）在全包 41 个 dex 里没有任何调用点**。它是个空壳，留给 QFix 热补丁在需要时注入实现。

## 3. 三条签名链路（核心机制）

### 3.1 分流开关：`QSecConfig.sign_strategy`

`QSec.getSignEntry()` 是唯一的对外签名入口，内部只有一行判断：

```smali
.method public getSignEntry(Ljava/lang/String;[B)[B
    sget v0, Lcom/tencent/mobileqq/qsec/qsecurity/QSecConfig;->sign_strategy:I
    if-nez v0, :cond_1b
    invoke-virtual {p0, p1, p2}, ...->getLiteSign(...)   # 策略 0：轻量链路
    :cond_1b
    invoke-virtual {p0, p1, p2}, ...->getSign(...)       # 策略非 0：完整链路
```

**含义**：走哪条签名链路完全由服务端控制。这既是灰度手段，也是降级手段——重链路被逆向或出问题时，服务端可以把全量用户切到轻链路。

### 3.2 完整链路：`ByteData`

```
QSec.getSign(moduleId, salt)
  └─ ByteData.getSign(QSecConfig.business_uin, moduleId, salt)
       └─ private native byte[] getByte(Context, Object)
```

异常时返回字符串 `"unsupported"` 的字节（`ByteData.smali` 里唯一的常量）。版本 `ByteData` 无 `getVersion`，实际实现全在 native。

### 3.3 轻量链路：`Dandelion`

```
QSec.getLiteSign(moduleId, salt)
  └─ Dandelion.fly(moduleId, salt)
       └─ private native byte[] energy(Object, Object)
```

`Dandelion` 版本号 `"0.0.4"`，`SecCipher` 版本 `"0.0.3"`，`QSec` 自身 `"0.0.1"` —— 三个独立迭代的组件版本，说明它们由不同团队/不同节奏维护。

**这三条链路（ByteData / Dandelion / SecCipher）的 native 实现都在 `libfekit.so` 里，通过 `JNI_OnLoad` 动态 `RegisterNatives` 注册，静态看不到任何 `Java_` 导出符号。**

## 4. 登录协议里的落点：TLV 544

这是风控签名**真正被使用**的地方。`tlv_t544.smali` 全文 326 行，结构完全清晰：

### 4.1 TLV 544 的 body 布局

```
get_tlv_544(long userID, String moduleID, int subCmd)
  ├─ int64  userID            (8B, 大端)
  ├─ int16  len(w.D)
  ├─ bytes  w.D               ← 设备 GUID（wtlogin 初始化时从文件读出）
  ├─ int16  len("6.0.0.2591")
  ├─ bytes  "6.0.0.2591"      ← 硬编码的 wtlogin SDK 版本
  └─ int32  subCmd
       ↓
     tlv body = QSec.getLiteSign(moduleID, 上面这坨字节)
```

注意 `w.D` 的来源：`w.h()`（wtlogin 的 init）里 `sput-object v0, Loicq/wlogin_sdk/request/w;->D:[B`，赋的是 `util.getGuidFromFile(context)` 的 clone。所以 **TLV 544 的 salt 就是设备 GUID**。

### 4.2 TLV 544 的旁路上报

同一个 TLV 在生成时还会同步上报两条日志：

```java
// 签名成功后
QSec.reportLog("sign_point", moduleID, hex(签名), buf_to_string(w.D));
// 发送前（TLV 544 的 report 静态方法）
QSec.reportLog("chk_point", <p0>, <p1>, buf_to_string(w.D));
```

`reportLog` → native `doReport(tag, key, value, salt)`。**即：每一次登录签名，都会额外把「签了什么 + 结果是什么 + 设备 GUID」回传一份。** 这是服务端做签名一致性审计的数据源。

### 4.3 调用方矩阵（xref 实测）

| 调用方 | 位置 | 调用 | 业务含义 |
|---|---|---|---|
| `oicq.wlogin_sdk.request.WtloginHelper` | classes2 | `getFeKitAttach` ×9 | 登录主流程，向 SDK 取 attach 数据 |
| `oicq.wlogin_sdk.tlv_type.tlv_t544` | classes6 | `getLiteSign` | 构建登录 TLV 544 的签名 |
| `oicq.wlogin_sdk.request.e0` / `r` | classes6 / classes11 | `getFeKitAttach` | 登录重试 / 其他请求路径 |
| `com.tencent.secprotocol.ByteData` | classes3 | `initSign` | 独立协议栈初始化 |
| `com.tencent.qqprotect.xps.core.AntEst` | classes3 | `getEstInfo` | 环境检测（est） |
| `com.tencent.mobileqq.jsp.bt` | classes8 | `getLiteSign` | H5 / JSBridge 侧调用 |
| `com.tencent.mobileqq.friend.servlet.coder.b` | classes8 | `initSign` | 好友协议编码器 |

## 6. 任务体系（服务端可编排）

`QSecConfig` 里定义了完整的任务模型：

```java
// 任务 ID
CONST_HEARTBEAT_TASK_ID    = 0
CONST_CONFIG_TASK_ID       = 1
CONST_KEYEXCHANGE_TASK_ID  = 2
CONST_LUA_TASK_ID          = 3     ← Lua 脚本执行槽
CONST_REPORT_TASK_ID       = 4

// 执行类型
DO_TYPE_START  = 1
DO_TYPE_STOP   = 2
DO_TYPE_INIT   = 3
DO_TYPE_DELE   = 4

// 配置字段
HEART_BEAT_SEQ_NUM   // 心跳序号
CONFIG_TIME_GAP      // 配置拉取间隔
CONFIG_KEY_ID        // 配置密钥 ID
CONFIG_KEY_BUF       // 配置密钥内容
```

驱动入口是 `QSec.execTasks(Context, int doType)` → native `doSomething(Context, int)`。

**`CONST_LUA_TASK_ID = 3` 是最值得警惕的一条**：风控体系预留了 Lua 脚本执行槽。这意味着服务端可以下发 Lua 脚本在客户端执行任意检测逻辑，而不需要发版。`QSec.smali` 里 `TASK_START` / `TASK_STOP` / `TASK_DELAY = 5000ms` 三个常量也印证了这是个常驻轮询体系。

### 6.1 环境检测（est）

```

  ├─ c(boolean) / f(int)  结果处理
```

## 7. 反调试与反 Hook 的三层设计

### 7.1 第一层：`libQSec.so`（28 KB 的专职壳）

dynsym 完全为空（strip 干净），但 dynstr 保留 `JNI_OnLoad`。导入符号暴露了它的全部行为：

```
dladdr     ← 取自身基址，做内存完整性自检
dlopen     ← 加载子模块 / 反注入
dlsym
sigaction  ← 安装信号处理器（拦截 SIGTRAP / SIGSEGV / SIGILL）
timer_create / timer_settime / timer_delete  ← 周期性检测
sleep
chmod
pthread_once / pthread_mutex_*
```

字符串里有两组反常的构造：

```
__a_b_c_d_e_f_i__aaaaa1234567_
__t_a_c_d_e_f_i__hhhhh1234567_
```

`timer_create` + `sigaction` + `dladdr` 的组合是标准写法：**定时器周期性检查自身内存是否被修改（对照 dladdr 拿到的基址和预期内容），同时捕获调试信号**。28 KB 装不下加密逻辑，它的职责纯粹是「检测并阻断」。

### 7.2 第二层：Matrix + ShadowHook

```
libmatrix-hookcommon.so     ← 枚举 inline hook 修改点
libmatrix-memoryhook.so     ← 内存 hook 检测
libmatrix-pthreadhook.so    ← pthread 层 hook 检测
libmatrix-traffic.so        ← 流量监控
libshadowhook.so            ← 腾讯自研 inline hook（bytehook 分支）
libbugly_shadowhook.so
libbugly_dumper.so
```

**这一层比 QSec 本身更难缠**：Matrix 的 memoryhook 会扫描常见 hook 框架留下的特征（GOT/PLT 改写、函数序言被替换为跳转）。frida 注入时最容易撞上的就是这里。

### 7.3 第三层：`QSec.detectMethod` —— 空壳

这是本次分析最意外的发现。全包 **41 个 dex、2,627,366 个 method_ids**，用自写的 DEX 指令扫描器（解析所有 `invoke-*` 的 method_idx）遍历后：

```
### 目标方法定义
  Lcom/tencent/mobileqq/qsec/qsecurity/QSec;->detectMethod

### 调用点 (caller -> target)
  无
```

**没有任何 Java 代码调用 `detectMethod`。** 同理 `getSign`、`getSignEntry`、`getXwDebugID` 也只在 `QSec` 内部自调，没有外部调用者。

再结合实现看：

```smali
.method public detectMethod(Ljava/lang/String;Ljava/lang/String;)Z
    const/4 v0, 0x0            # 默认返回 false
    const/4 v1, 0x1
    :try_start_19
    invoke-static {p1}, Ljava/lang/Class;->forName(...)     # 按类名加载
    invoke-virtual {p1}, Ljava/lang/Class;->getDeclaredMethods()[...
    ... 遍历方法名，命中返回 true
    :catchall_35
    ... log "DM:" + exception
    :cond_4b
    return v0                  # 异常/未命中返回 false
```

**判定**：这是一个**预留接口**。QFix 是热修复框架，配合 `$redirector_` 机制，腾讯可以在需要时通过补丁把 `detectMethod` 从"空壳返回 false"换成真正的检测实现，而 `getSign` 的空壳位置换成真正的签名调用。这解释了为什么类结构极其规整（每个方法都有 redirector 样板）但大量方法没有调用者——**代码是按「可热替换」设计的**。

**对分析的意义**：想通过 hook `detectMethod` 来绕过检测是无效的——因为它现在根本不执行检测。真正的检测在 `libQSec.so` 的定时器和 Matrix 的 native 扫描里。

## 8. 加密配置文件

### 8.1 两个文件的真实结构

| 文件 | 大小 | magic | 熵 | 判定 |
|---|---|---|---|---|
| `txsfcfg.dat` | 54,186 B | `Schk` | 3.651 | **7-bit 字符表编码**（非加密） |
| `qself.dat` | 18,160 B | `self` | 5.990 | GBK 双字节密集 + 二进制混合，接近密文 |

### 8.2 `txsfcfg.dat` 头部（大端）

```
53 63 68 6b   "Schk"
00 00 00 80   0x80            ← 长度或标志
01 00 00 00   1               ← 版本
6a a9 4a 09   0x6AA94A09 = 1789479433 → 2026-09-15 13:37:13 UTC   ← 生成时间
00 00 00 f4   244             ← 条目数
```

（`Schk` 的 `k` 大写，指的是 **Security Check**）

### 8.3 7-bit 字符表编码（已确认）

对 body 做 UTF-8 三字节序列提取，结果：

```
合法 UTF-8 3 字节序列: 18,013 个
码点范围:  U+4A22 .. U+5C49
不同码点数: 71
落在 [U+4A00, U+4A80) 内: 18,012 / 18,013 = 100.0%
```

**`U+4A00` 到 `U+4A7F` 恰好是 128 个连续码点，即每个字符携带 7 bit。** 这是把二进制数据伪装成「CJK 扩展 A 区生僻字」的隐写式编码，观感上像一堆乱码汉字。

去掉基址后的 7-bit 值序列：

```
104 122 122 108 125 122 | 38 101 96 107 | 38 113 49 63 86 63 61 | 38 101 96 107
```

**并呈现出明确的重复记录结构** —— 同一串 `104 122 122 108 125 122`（= `68 7a 7a 6c 7d 7a`）在流中反复出现，`38 101 96 107`（= `26 65 60 6b`）作为固定字段出现多次。

这高度符合「**规则表**」的形态：每条规则有相同的记录头（规则 ID / 类型），后跟不同的参数段。翻译成 `Schk` 的语义，就是服务端下发的**风控检查规则集合**。

**未完成的部分**：7-bit 值到原始字节的位重打包（LSB-first / MSB-first / 各种位偏移）都试过，未得到可读文本或已知容器（zlib/gzip/protobuf）头。说明编码之上还有一层变换（可能是与 `assets/qq.key` 或 `CONFIG_KEY_BUF` 相关的流密码）。

### 8.4 `qself.dat`

GBK 双字节能解出 8,820 个字符，覆盖 U+4E07..U+FE3F 共 3,088 个不同码点，跨度 45,113 —— **纯随机的宽分布**，不是文本。前 16 字节：

```
73 65 6c 66   "self"
00 00 00 01   1        ← 版本
a5 49 3b 3f   0xA5493B3F
00 00 46 5c   17,500   ← 长度字段
```

`a5 49 3b 3f` 若按大端时间戳解释 = 2772597567，超出合理范围；按小端 = 1059734949（2003 年），也不对。可能是 CRC 或校验值。`0x465c = 17500` 与文件剩余长度（18144）接近，**很可能是 body 长度字段**。

`self` 语义是自校验：这个文件是「自身的完整性基线」，启动时与当前 so/dex 的实际校验值比对。

加上 `QSecConfig.CONFIG_KEY_ID` / `CONFIG_KEY_BUF` 与 `CNativeConfigStore` 的对应关系——**`txsfcfg.dat` 的密钥很可能就是通过 `CNativeConfigStore` 拿到的**。

### 9.2 `libfekit.so`（7.28 MB）—— 真正的风控后端，但被混淆

```
00341554   31024 B   .datadiv_decode4609666545228600477
000822b4   44380 B   JNI_OnLoad
```

`.datadiv_decode<随机数>` 是 **OLLVM `-data-div` / Hikari 字符串加密**的标志。44 KB 的 `JNI_OnLoad` 意味着上千个 `RegisterNatives` 全在运行时绑定，静态看不到任何 `Java_com_tencent_mobileqq_qsec_*` 导出。

**`ByteData.getByte` / `Dandelion.energy` / `SecCipher.codec` / `QSec.get11` / `getXwDebugID` / `doReport` / `doSomething` / `QQSecuritySign.getSign` 全部在这一个 so 里。**

## 10. 攻击面排序（按投入产出）

| 优先级 | 目标 | 做法 | 预期收益 |
|---|---|---|---|
| **P0** | `libmsfbootV2.so` 的 `CMSFJavaUtil::IsSignatureValid` | unidbg 加载，构造 jobject 调 1108 字节的函数 | 直接决定改包能不能跑，是重打包第一道门 |
| **P0** | `libmsfbootV2.so` 的 `QSCrypt::Encrypt/Decrypt` | unidbg 黑盒，构造输入看输出 | 拿到 QSec 的对称加密原语 |
| **P1** | `FEKit.loadSoAsync()` 热更新路径 | 抓下载 URL 与校验逻辑 | **若能替换 so，等于接管全部风控**；这是架构上最大的单点 |
| **P1** | `IPatchRedirector` 伪造 | 实现一个 `hasPatch()→true` 的 redirector 塞进 `PatchRedirectCenter` | 一处接管所有 QFix 插桩过的方法，比逐个 hook 干净 |
| **P1** | TLV 544 输入输出对 | 真机 hook `tlv_t544.get_tlv_544`，记录 (moduleID, GUID, subCmd) → sign | 拿到签名前后的完整映射，用于离线复现 |
| **P2** | `libfekit.so` 的 OLLVM 字符串解密 | Ghidra headless，先跑 `.datadiv_decode` 交叉引用，还原 `JNI_OnLoad` 的注册表 | 拿到全部 QSec native 方法名单 |
| **P3** | `txsfcfg.dat` 的 7-bit 编码还原 | 结合 `CNativeConfigStore` / `CONFIG_KEY_BUF` 找上层的流密码 | 拿到完整风控规则表，可预判检测点 |

**明确无效的方向**：
- hook `QSec.detectMethod` —— 无调用点，hook 了也没效果
- 靠改 `sign_strategy` 切换链路 —— 两条链路的 native 实现在同一个 so，绕不过
- 模拟器动态 —— 纯 arm64 + 无硬件加速，且 `libQSec.so` 的定时器 + Matrix 的 memoryhook 会立刻发现
