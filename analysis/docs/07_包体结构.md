### 2.3 关键发现

**`detectMethod(String className, String methodName)`** —— 反射遍历 `Class.getDeclaredMethods()` 匹配方法名。这是**反 Hook 检测原语**：传入 `"de.robv.android.xposed.XposedBridge"` 之类的类名和方法名，看能不能找到。调用方通过参数决定检测什么，所以 strings 里看不到 "frida"/"xposed"，全类名扫描 0 命中是正常的——检测目标是**运行时传入的**。

**`QSec.smali` 里的全部字符串常量**：

```
"0123456789ABCDEF"   hex 表
"FEKit_QSec"         log tag
"DM:" / "attach cmd:" / ",subcmd:" / " ,xw pb is:"   日志格式
"exception:"
"qq.key"             ← 加载 assets/qq.key
""
```

**`features/versions`**：`Dandelion.getVersion()` = `"0.0.4"`，`SecCipher.getVersion()` = `"0.0.3"`，`QSec.sVersion` = `"0.0.1"`。三个独立迭代的 SDK 版本。

**`Dandelion.fly(String, byte[])`** → `private native byte[] energy(Object, Object)` —— "蒲公英" 是数据中继/加密通道，参数和返回值都是裸字节流，看不出语义（native 里）。

**`ByteData.getSign(String, String, byte[])`** → `private native byte[] getByte(Context, Object)` —— 签名入口，失败返回 `"unsupported"`。

**`SecCipher.encrypt/decrypt(String)`** → `private native Object codec(Object, int)` —— 返回 `SecInfo` 对象，int 是模式位。

### 2.4 QFix 插桩的影响

**每一个方法**开头都是这段样板：

```smali
sget-object v0, Lcom/tencent/mobileqq/qsec/qsecurity/QSec;->$redirector_:Lcom/tencent/mobileqq/qfix/redirect/IPatchRedirector;
if-eqz v0, :cond_17
const/16 v1, 0xe                       # 方法编号
invoke-interface {v0, v1}, ...->hasPatch(S)Z
invoke-interface {v0, v1, p0, p1, p2}, ...->redirect(...)Ljava/lang/Object;
```

含义与影响：

1. **热修复能力是真的** —— 腾讯可以在不发版的情况下替换 `getSign`/`detectMethod` 的实现
2. **静态分析会看到双份逻辑** —— 每个方法体实际是 `if (patch) {...} else {原实现}`，读代码时必须跳过样板
3. **动态 hook 有两个入口** —— 可以 hook 原实现，也可以伪造一个 `IPatchRedirector` 让 `hasPatch()` 返回 true，直接接管返回值。**后者更隐蔽**
4. **`PatchRedirectCenter.getRedirector(int)`** 是所有类的总入口，改它一处即可拦截全部

### 3.2 `libkernel.so`（50.94 MB）— QQNT 内核

未 strip，3,674 个 dynsym / **3,579 个 FUNC 导出**。段布局：

```

.rodata         3,593,589 B
```

导出符号**几乎全是 `Java_com_tencent_qqnt_kernel_nativeinterface_*_00024CppProxy_native_1*`** —— 即 Chromium 风格的 CppProxy 自动生成层。例：

```
Java_..._IKernelProfileService_00024CppProxy_native_1updateStockLocalData
Java_..._IKernelStorageCleanService_00024CppProxy_native_1addCacheScanedPaths
Java_..._IQQNTWrapperSession_00024CppProxy_native_1init

```

**含义**：`libkernel.so` 是 QQNT 架构的 C++ 内核（会话、消息、存储、资料），导出面巨大但每个函数都只是薄薄一层 CppProxy 转发到内部 `nt::` 实现。要从这里逆协议，得先找到内部实现——工作量远大于 `libmsfbootV2.so`。

### 3.3 `libfekit.so`（7.28 MB）— OLLVM 混淆

1,598 个 FUNC 导出 / 669 个 OBJECT。决定性证据：

```
00341554   31024 B   .datadiv_decode4609666545228600477
000822b4   44380 B   JNI_OnLoad
```

`.datadiv_decode<随机数>` 是 **OLLVM `-data-div` / Hikari 混淆器的字符串加密函数**特征命名。`JNI_OnLoad` 有 **44 KB** —— 内含上千个 `RegisterNatives` 调用，全部 JNI 方法在运行时动态绑定，静态 `Java_*` 导出基本为 0（除杂项）。

**结论**：`libfekit.so` 是 QSec 真正的 native 后端（`Dandelion.energy`、`SecCipher.codec`、`QSec.get11` 应该都在这里注册），但符号不可读、字符串加密，**必须动态 dump 或 unidbg + trace 才能定位**。

### 3.4 `libQSec.so`（28 KB）— 反调试壳

dynsym **完全为空**（strip 干净，但保留 `JNI_OnLoad` 在 dynstr）。导入的高危符号：

```
dladdr        ← 取自身基址，做完整性自检
dlopen        ← 加载子模块 / 反注入
dlsym
sigaction     ← 安装信号处理器（拦截 SIGTRAP/SIGSEGV）
timer_create / timer_settime / timer_delete   ← 定时轮询检测
sleep
chmod
write
pthread_once / pthread_mutex_*
```

字符串里有两组反常的构造：

```
__a_b_c_d_e_f_i__aaaaa1234567_
__t_a_c_d_e_f_i__hhhhh1234567_
```

**判定：这是一个独立的反调试 / 自校验小壳**。`timer_create` + `sigaction` + `dladdr` 的组合是"定时器周期性检查自身内存完整性 + 捕获调试信号"的标准写法。28 KB 装不下真正的加密逻辑，它的职责是**检测并阻断**，真正的加密在 `libfekit.so`。

## 7. 下一步建议（按投入产出排序）

| 优先级 | 动作 | 理由 |
|---|---|---|
| **P0** | unidbg 加载 `libmsfbootV2.so`，补 `QSCrypt::Encrypt/Decrypt` 调用 | 符号全、函数小、逻辑自洽。这是**唯一能低成本黑盒拿到结果**的 native 目标 |
| **P0** | 读 `libmsfbootV2.so` 的 `CMSFJavaUtil::IsSignatureValid` 伪代码 | 1108 字节，直接决定"改包后能不能跑"，是重打包的第一道门 |
| **P1** | 真机（arm64）+ frida，先 hook `IPatchRedirector.hasPatch` 返回 false | 关掉 QFix 插桩层，让所有方法走原实现，输出干净得多 |
| **P1** | hook `QSec.detectMethod` 返回 false，`ByteData.getSign`/`Dandelion.energy` 打输入输出 | 绕过反 Hook 检测 + 抓签名输入输出对 |
| **P2** | 解 `assets/wxa_dynamic_pkg...zip` 和 `assets/KingkongPatch.apk` | 未加密，直接 `unzip` 即可，可能有未混淆代码 |
| **P3** | Ghidra headless 批处理 `libfekit.so`，先跑 `.datadiv_decode` 交叉引用 | 需要先解 OLLVM 字符串加密才能读 JNI_OnLoad 的注册表 |
| **P4** | `libkernel.so` 内部 `nt::` 实现 | 30 MB .text + CppProxy 薄层，投入产出比最低 |

**明确不建议**：模拟器这条路。三重阻塞——纯 arm64、AEHD/WHPX 都没装、本机 6.94 GB 内存。买/借一台 arm64 安卓机（Android 9+，可 root）比在模拟器上折腾省几十小时。
