## Part 0 · 摘要与结论

### 0.1 一句话

QQ 的防护是**三层结构**：业务加密（不设防）+ 环境检测（重度）+ 服务端判定（不可见）。
**客户端能改的只有前两层，决策权永远在服务端。**

### 0.2 关键数字

| 指标 | 数值 |
|---|---|
| APK 大小 | 373.86 MiB |
| ZIP 条目 | 40,571 |
| dex 数量 | 41 |
| 去重类数 | 430,761 |
| 方法总数 | 2,627,366 |
| native 库 | 200 个（全 arm64-v8a） |
| 检测强度 ≥20 的库 | 7 个 |
| 需 hook 的 libc 函数（去重） | 39 |
| 直接系统调用 `svc #0` | 116 处（9 个库） |

### 0.3 最重要的四条结论

1. **QSCrypt 的 TEA 已完整还原**（三个 native 向量验证通过），可直接用 Python 复现。
2. **腾讯支付国密库未做任何算法魔改**，SM3/SM4 与国标向量完全一致，可用标准实现替代。
3. **周期性掉线是 1800 秒定时体检**，不是实时检测（`libfekit` / `libbasic_share` / `libMSFKernel` 三库均为常量 `1800`）。
4. **`dl_iterate_phdr` 是 7/7 全覆盖的枚举入口**，守住这一个函数等于一次覆盖全部检测库。

### 2.2 签名链路

`QSecConfig.sign_strategy` 是三值开关：

```
strategy == 0  →  getLiteSign → Dandelion.fly() → native energy()
strategy != 0  →  getSign     → ByteData.getSign() → native getByte()
```

**xref 实测**：`getSign`（完整链路）只有 `QSec` 自己内部调用，外部全是 `getLiteSign`。说明现网 `sign_strategy` 大概率是 **0**。

### 2.3 TLV 544 —— 签名真正落地处

```
get_tlv_544(long userID, String moduleID, int subCmd)
  ├─ int64  userID
  ├─ int16  len(w.D) + bytes w.D      ← 设备 GUID（w.h() 从文件读）
  ├─ int16  len("6.0.0.2591") + 版本串
  └─ int32  subCmd
       ↓
     QSec.getLiteSign(moduleID, 上面这坨)
```

每次签名后，还会旁路调 `QSec.reportLog("sign_point", ...)` 把「签了什么 + 结果 + GUID」回传一份，用于服务端做一致性审计。

### 2.4 `detectMethod` 是空壳

DEX 指令全扫（41 dex / 2,627,366 method_ids）结果：

```
目标定义: Lcom/tencent/mobileqq/qsec/qsecurity/QSec;->detectMethod
调用点  : 无
```

同理 `SocketStatus.checkSocket` 也是零调用方。

**它们是 QFix 热补丁的预留接口** —— 配合 `$redirector_` 机制，腾讯可以在需要时把实现注入进去。

**实践含义**：hook `detectMethod` 无效（它现在不执行任何东西）。真正的检测在 `libQSec.so` 的定时器和 `libfekit` 的 `RuntimeEnvCensorTask` 里。

### 3.2 【已完整还原】QSCrypt

**标准 TEA，16 轮，delta = `0x9E3779B9`，输入/密钥/输出全部大端。**

三个 native 向量（unidbg 实测，全部吻合）：

| 明文 | 密钥 | native 输出 |
|---|---|---|
| `0011223344556677` | `000102…0f` | `205f515574f0821c` |
| `0000000000000000` | 全零 | `a889f798182d8083` |
| `0102030405060708` | `000102…0f` | `6ac3f66fac01d1ad` |

**封装结构**（TEA + CBC 链 + rand() IV）：

```
Encrypt:
  IV₁ = R                     ← 8 字节，来自 rand()
  T_i = TeaEncryptECB(P_i ^ IV_i, KEY)
  C_i = T_i ^ IV_i
  IV_{i+1} = T_i

Decrypt:
  IV = R
  T_i = C_i ^ IV_i
  P_i = TeaDecryptECB(T_i) ^ IV_i
  IV_{i+1} = T_i
```

**输出长度**：`8 + 8·ceil((len+1)/8)`

**对象布局**：

```
QSCrypt(uchar* key, uchar X2, uchar X3, uchar X4)
   [0x00] vtable
   [0x08] key[0..15]
   [0x18] X2 = Encrypt 开关  ← 必须 0
   [0x19] X3 = Decrypt 开关  ← 必须非 0
```

**关键坑**：`[0x18]` 是模式位，不是密钥长度。传错会导致加解密静默返回空。

**`Decrypt` 有自校验**：逐字节比对解密结果与输入，不等则返回 0。因此它只吃 `Encrypt` 产出的合法数据。

**可用脚本**：`qscrypt.py`（自检全过，可直接 enc/dec）

### 3.3 【已跑通】腾讯支付国密

**关键突破：一个全局标志**

```asm
120630a8  adrp  x0, #0x120be000
120630ac  ldr   w0, [x0, #0xcc8]    ← 读一个全局 int
120630b0  ret
```

初始值 `-1`，SM3/SM4/SM2 全部返回错误。写 `0` 即可：

```java
UnidbgPointer.pointer(emulator, module.base + 0xbecc8).setInt(0, 0);
```

**验证结果**（全部国标向量）：

| 函数 | 输出 | 标准 |
|---|---|---|
| `md5("")` | `d41d8cd98f00b204e9800998ecf8427e` | RFC 1321 ✔ |
| `sha1("abc")` | `a9993e364706816aba3e25717850c26c9cd0d89d` | FIPS 180-4 ✔ |
| `sha256("abc")` | `ba7816bf8f01cfea…f20015ad` | FIPS 180-4 ✔ |
| `sm3("abc")` | `66c7f0f462eeedd9…8f4ba8e0` | GB/T 32905 ✔ |
| `sm4Cbc` 首块 | `681edf34d206965e86b3e94f536e4246` | GB/T 32907 ✔ |
| `sm2GenKeyPair` | 32B 私钥 + 65B 公钥（`04‖X‖Y`） | 标准 SM2 ✔ |

**结论：腾讯没有做任何算法魔改，就是标准国密。**

**未完成**：`sm2Sign` / `sm2Encrypt` 返回 `-10001`（长度校验失败）。4 个 `byte[]` 参数的语义组合还没试对。但 SM3/SM4 是基础原语，SM2 可用标准库替代。

**可用脚本**：`gm_crypto.py`（纯 Python SM3/SM4，零依赖，向量全过）

### 3.4 【部分突破】txsfcfg.dat

**文件结构**：

```
offset 0    "Schk"                          magic（Security Check）
offset 4    BE32 0x80                       长度/标志
offset 8    BE32 1                          版本
offset 12   BE32 0x6AA94A09 = 1789479433    → 2026-09-15 13:37:13 UTC
offset 16   BE32 0xF4 = 244                 条目数
offset 22   body                            7-bit 字符表编码
```

**7-bit 编码（已完全解出）**：

每个 UTF-8 三字节序列的码点都落在 `[U+4A00, U+4A80)` —— 恰好 128 个连续码点，即每字符携带 7 bit。这是把二进制伪装成 CJK 扩展 A 区生僻字的隐写式编码。

实测：18,013 个三字节序列，**100% 落在该区间**，不同码点 71 个。

**密码层未解开**：做了 16,386 个密钥候选的系统性穷举（`qq.key`/`fekit.key` 全文滑窗、protobuf 字段、文件头派生、三种位重排），全部未命中。

**原因确定**：`QSecConfig.CONFIG_KEY_BUF` 的 `<clinit>` 初值是 `null`，只有 `setupBusinessInfo` 会填充，而参数来自**服务端**。密钥不在 APK 里。

### 3.5 密钥容器格式

`qq.key` 和 `fekit.key` **头部完全相同**，是 protobuf 包装：

```
#1  varint 1                 version
#2  varint 1                 type
#3  bytes(16) "VsXd9s4v5y/A?s(G"
#4  varint 12384             载荷长度
#10 bytes(128)               密文/校验块
#11 bytes(147456)            fekit 独有
#12 bytes(64)                fekit 独有
```

## Part 5 · 周期性掉线根因与修复规格

> 完整版见 `KICK_FIX_SPEC.md`，此处为摘要。

### 5.1 根因：1800 秒定时体检

| 库 | 常量 | 出现次数 |
|---|---|---|
| `libfekit.so` | `1800`（30 分钟·秒） | ×4 |
| `libfekit.so` | `5400`（90 分钟·秒） | ×1 |
| `libbasic_share.so` | `1800` | ×7 |

| `libMSFKernel.so` | `1800` | ×3 |
| `libMSFKernel.so` | `300000`（5 分钟·毫秒） | ×1 |

### 5.2 触发链

```
1800s 到期
  → RuntimeEnvCensorTask（libfekit @0x44020e）
  → dl_iterate_phdr()        ← 7/7 库全部导入
  → 拿到模块 so 完整路径（带包名，改名无效）
  → fopen("/proc/self/maps") 二次确认
  → trpc.o3.report.SsoReport
  → 服务端判定 → StatSvc.ReqMSFOffline (2012) → 踢线
```

### 5.3 三个修复点

**P0 — `dl_iterate_phdr`**

清空模块的 `dlpi_name`（不要改假名字，空串是主程序镜像的正常形态）：

```c
static int my_callback(struct dl_phdr_info *info, size_t size, void *p) {
    if (info->dlpi_name && is_module_path(info->dlpi_name)) {
        struct dl_phdr_info copy = *info;
        copy.dlpi_name = "";        // 伪装成主程序镜像
        return user_cb(&copy, size, data);
    }
    return user_cb(info, size, data);
}
```

**P0 — bytehook soname 隔离**

模块的 bytehook 改 `OUTPUT_NAME`，避免与 QQ 的 `libbytehook.so` 共用实例（否则 `bytehook_get_records` 能列出你的 hook）。

**P1 — `/proc/self/maps`**

用 `memfd_create` 构造真实 fd 返回过滤内容（`fmemopen` 的 FILE* 无真实 fd，`fileno()` 会失败）。

### 6.3 关键方法：`.init_array` 手动执行

unidbg 的 `loadLibrary` **不执行 `.init_array`**，导致 OLLVM 的 `.datadiv_decode` 从不运行。

```java
// 读 .init_array 表
UnidbgPointer arr = UnidbgPointer.pointer(emu, module.base + 0x731898);
for (int i = 0; i < 37; i++) {
    long fn = arr.getLong(i * 8L);
    module.callFunction(emu, fn - module.base);   // ← 传相对偏移！
}
```

**关键坑**：`callFunction` 需要**相对偏移**，不是绝对地址。传绝对地址会跳到 `base + abs`（不存在的地址）。

### 6.4 结论：libfekit 无法静态解密

执行全部 37 个 init 函数后，`.rodata` 差异为 **0**。48,886 字节的差异全在 `.data`，且都是指针值被清零（重定位），不是字符串解密。

**判定**：`.datadiv_decode` 是**在每个函数内部按需调用**的，函数不执行就不解密。静态解密整个库这条路走不通。

### 7.3 边界认知

```
客户端：采集环境 → 上报
服务端：判定 → 决定要不要升权（人脸/短信/封号）
```

**决策权在服务端。** 客户端改得再干净，只是改变"上报上去的内容"，不能改变"服务端已经知道的历史"。

这也解释了为什么 QB 项目反复强调「源头消除特征」而不是「末端拦截」——**只有在第一次采集之前就完成伪装，服务端才拿不到脏数据。**
